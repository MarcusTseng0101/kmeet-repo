# Walkthrough - K-Meet 開發決策日誌

## 決策點 1：邀請函導向 (Invitation-Centric)
- **問題**：傳統交友軟體看臉太膚淺，且線上合唱缺乏真實社交感。
- **解決方案**：將 5 首必唱歌曲放入邀請函，讓「想唱什麼」成為媒合的第一指標。
- **實作**：`TabInvitation` 強制要求 5 首必唱 + 2 首備案才能發布，並即時顯示 `detectGenre()` 標籤。

## 決策點 2：應對店家歌單動態更新
- **挑戰**：店家會剔除舊歌，且 J-pop 在某些分店極少。
- **解決方案**：
  1. 放棄序號點歌，改用「搜尋關鍵字輔助」。
  2. 建立「存活率標籤」，根據用戶歷史回報，推薦 J-pop 較齊全的店家。
  3. 引入「備選歌單」，當必唱歌曲失效時立即補位。
- **實作**：`handleNotFound()` 每次觸發 -8 分衰減，`venueScores` 提升至頂層 state 確保跨 tab 持久；備案 panel 以滑入動畫彈出並列出三組搜尋關鍵字 chip。

## 決策點 3：公平性與社交節奏
- **挑戰**：一群陌生人見面，點歌順序容易混亂。
- **解決方案**：開發「公平輪唱排程」，App 自動分配每個人在每個輪次的點歌位，並允許新加入者在當前輪次結束後公平插入。
- **實作**：`buildFlatRotation()` 以不可變 `slotIdx` 為游標，`lateJoiners` 在輪次邊界插入，確保排程確定性。

## 決策點 4：重複歌曲偵測（v0.2.0 新增）
- **問題**：若參與者提議的歌曲已在主揪必唱清單中，會造成歌單單調。
- **解決方案**：`takenSongs` 計算主揪必唱 ∪ 所有已確認參與者歌單，點擊重複歌曲立即彈出 `⚠️` 警示，提供「換一首」或「還是要加」兩個出口。

## 技術取捨紀錄
| 議題 | 選擇 | 原因 |
|------|------|------|
| 狀態管理 | React useState（提升至 KMeet） | 原型階段無需 Redux，props drilling 範圍可控 |
| 存活率儲存 | `venueScores` object | key = `venueId_songId`，O(1) 查詢，易序列化 |
| 輪唱游標 | slotIdx（不可變索引） | 避免 late-join 後 done-count 與 slot 錯位 |
| 歌曲搜尋 | 本地 filter | 原型用靜態 SONG_POOL；正式版替換為 API |
